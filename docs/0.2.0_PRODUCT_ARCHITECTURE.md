# GTFS Explorer 0.2.0 — Arquitectura del editor visual

Estado: `DELTA_BASED_REVISION_MODEL_IMPLEMENTED`  
Fecha: 2026-09-03  
Alcance: diseño vinculante para el único ciclo continuo 0.2.0. No implementa
ni altera la release 0.1.0.

## 0.2.0_PRODUCT_ARCHITECTURE

0.2.0 extiende el producto local y offline-first con edición GTFS visual,
auditable y no destructiva. Conserva las capas existentes y añade un módulo
`editing` en dominio, aplicación, infraestructura y presentación. La UI nunca
escribe DuckDB ni el mapa decide cambios: ambos solicitan comandos de
aplicación validados.

```text
Fuente GTFS inmutable -> ORIGINAL_GTFS -> WORKING_COPY -> DRAFT/CHANGESET
                                                      -> validación -> exportación

Qt + MapLibre -> casos de uso de edición -> dominio/puertos -> DuckDB
      ^                 |                         |
      |                 +-> estado de selección    +-> historial y revisiones
      +---- bridge v2 restringido / GeoJSON incremental
```

`ORIGINAL_GTFS` es el estado de importación identificado por manifiesto y
SHA-256; se consulta pero jamás se modifica. `WORKING_COPY` es la última
revisión confirmada por el usuario. Cada edición se realiza contra un
`CHANGESET` de borrador materializado, que puede guardarse, descartarse o
confirmarse atómicamente hacia una nueva revisión de trabajo. Ninguna acción
reescribe el ZIP o directorio de origen.

La revisión `original` es la revisión 0 implícita: no se crea una fila con una
instantánea del feed. `editor_state` conserva el baseline y el cursor del
borrador; `editor_deltas` es su materializado recuperable. Las revisiones
publicadas guardan únicamente metadatos y filas de
`editor_revision_deltas`, una por entidad modificada o eliminada. La
reconstrucción aplica la cadena de deltas sobre `ORIGINAL_GTFS`, dejando la
compactación/checkpoints para una evolución posterior.

Las vistas principales serán **Proyecto**, **Explorar**, **Editar**,
**Validación** y **Exportación**. Editar usa un workspace de tres paneles:
árbol de rutas/capas/entidades a la izquierda, un único `MapWidget` existente
en el centro y propiedades, cambios e incidencias a la derecha. No se crea un
segundo motor ni una segunda vista WebEngine.

## EDITING_DOMAIN_MODEL

Los agregados de edición son `ProjectRevision`, `WorkingCopy`, `ChangeSet`,
`EditorCommand`, `ValidationImpact` y `RouteWorkspaceState`.

| Concepto | Regla |
| --- | --- |
| OriginalRevision | Estado de solo lectura creado al importar o al migrar un proyecto 0.1.0. Conserva manifiesto, tablas fieles y modelo tipado. |
| WorkingRevision | Estado lógico GTFS reconstruido desde `original` y una cadena de deltas; solo cambia mediante confirmación de un ChangeSet y es la fuente de las exportaciones 0.2.0. |
| ChangeSet | Borrador persistente ligado a una WorkingRevision concreta; contiene comandos ordenados, estado de guardado y resultados de validación. |
| DraftRevision | Materialización privada en memoria de un ChangeSet sobre la WorkingRevision. Es lo que ve el editor y permite consultas simples, matrices y mapa sin interpretar un log en cada consulta. |
| EntityKey | UUID interno estable por entidad. Permite renombrar IDs GTFS sin perder selección, historial ni referencias de comandos. Los IDs GTFS siguen siendo los publicados. |
| Revision | Inmutable una vez confirmada; enlaza padre, autor local opcional, fecha, ChangeSet y resumen de impacto. No hay cuentas ni colaboración remota. |

El modelo GTFS actual mantiene sus lexemas, incluidos horarios superiores a
24:00. Las tablas de borrador conservan también el valor de presentación
(`arrival_time_lexeme`, `departure_time_lexeme`) y el valor de cálculo en
segundos; nunca convierten automáticamente 24:xx a otra fecha.

Las relaciones se controlan explícitamente:

- borrar una parada muestra sus `stop_times`, rutas, viajes y geometrías
  afectados; requiere elegir eliminar/reasignar/cancelar, sin sustitución
  inventada;
- mover o renombrar una parada no reordena `stop_times` ni altera horarios;
- reordenar una parada actúa sobre un viaje o patrón seleccionado, recalcula
  solo la secuencia objetivo y deja horarios como están hasta una decisión del
  usuario;
- editar o borrar un shape muestra los viajes que lo usan; no crea una
  geometría alternativa;
- cambiar `route_id`, `trip_id`, `service_id` o `agency_id` se trata como
  actualización con análisis de referencias antes de poder confirmar;
- crear una parada para un viaje ofrece exactamente «Introducir horarios»,
  «Ver interpolación» o «Dejar sin resolver». La interpolación es una vista
  previa que exige aceptación explícita y nunca se aplica al elegir la tercera
  opción.

## WORKING_COPY_MODEL

La implementación persistente privilegia coherencia y recuperabilidad sin
duplicar el feed completo: el staging y las tablas `gtfs_*` originales
permanecen intactos; `editor_deltas` contiene solo el borrador respecto de su
base; y `editor_revision_deltas` contiene solo los cambios inmutables de cada
revisión publicada. La creación de un borrador materializa en memoria el
estado lógico `ORIGINAL_GTFS + cadena de deltas`, y toda mutación afecta solo
al borrador y su comando. La confirmación publica metadatos y deltas en una
transacción; cancelar restablece el borrador desde la revisión base.

Este modelo evita una proyección SQL de eventos difícil de mantener para las
relaciones GTFS y elimina el parámetro JSON monolítico de la migración y la
publicación. La compactación/checkpoints queda preparada, pero no se activa
hasta que una medición justifique su necesidad.

Estados visibles:

| Estado | Significado | Acción de salida |
| --- | --- | --- |
| CLEAN | El borrador coincide con la WorkingRevision. | Editar. |
| DIRTY | Hay comandos aplicados después del último guardado del borrador. | Guardar borrador, descartar o confirmar. |
| SAVED_DRAFT | El borrador y su historial están persistidos, pero aún no son la WorkingRevision. | Continuar, descartar o confirmar. |
| COMMITTING | Transacción de publicación o validación de precondiciones en curso. | Esperar o recuperación conservadora tras corte. |
| CONFLICTED | Falló una precondición, una referencia o una migración. | Resolver o descartar; nunca sobrescribir. |

Cerrar/cambiar proyecto con `DIRTY` ofrece Guardar borrador, Descartar cambios
o Cancelar. Guardar un borrador no exporta ni publica. Confirmar cambios exige
un resumen de entidades, incidencias nuevas/resueltas y avisos sin resolver;
los errores bloqueantes de integridad impiden confirmar, las advertencias no.

## CHANGESET_MODEL

Un `ChangeSet` se almacena con `changeset_id`, `base_revision_id`, estado,
checkpoint de guardado y una secuencia inmutable de comandos. Cada
`EditorCommand` contiene:

```text
command_id, changeset_id, sequence, kind, entity_keys,
before, after, precondition_hash, impact, created_at, inverse_of, metadata
```

`before` y `after` son payloads JSON canónicos y acotados, no SQL ni código.
`precondition_hash` evita aplicar una operación sobre un borrador distinto del
que la originó. `impact` enumera entidades, tablas y reglas de validación
afectadas. Los comandos compuestos, por ejemplo insertar una parada y sus
stop_times, forman una unidad transaccional con suboperaciones ordenadas.

Los tipos iniciales son exactamente: `ADD_STOP`, `DELETE_STOP`, `MOVE_STOP`,
`UPDATE_STOP`, `REORDER_STOP`, `DELETE_ROUTE`, `UPDATE_SHAPE`, `ADD_SHAPE_POINT`,
`MOVE_SHAPE_POINT`, `DELETE_SHAPE_POINT`, `UPDATE_ROUTE`, `UPDATE_TRIP`,
`UPDATE_STOP_TIME`, `UPDATE_SERVICE`, `UPDATE_AGENCY` y `UPDATE_ATTRIBUTION`.
Los auxiliares internos (`ASSIGN_STOP_TO_TRIP`, `UNASSIGN_STOP_FROM_TRIP`,
`SET_ROUTE_WORKSPACE_STATE`, `COMMIT_CHANGESET`) no sustituyen ni esconden los
anteriores: dejan trazabilidad cuando la UI ejecuta una acción compuesta.

Aplicar un comando valida sus precondiciones, actualiza `draft_*`, registra el
evento y publica un impacto. Si una parte falla, la transacción completa hace
rollback. La UI no puede emitir un `UPDATE_*` parcial que el dominio no admita.

## UNDO_REDO_MODEL

Undo y redo son operaciones locales sobre la pila lineal del ChangeSet activo;
no son restauraciones de fichero. Cada `UNDO`/`REDO` queda también como evento
de auditoría, referencia el comando objetivo y aplica su `before`/`after` de
forma transaccional. Por ello el historial muestra tanto la intención original
como quién la invirtió y cuándo, incluso tras reabrir el proyecto.

Solo se puede deshacer el último comando efectivo y rehacer el último comando
deshecho. Ejecutar una edición nueva tras deshacer invalida la rama redo en el
estado activo, pero conserva sus eventos como rama histórica no activa. Los
comandos de confirmación no se deshacen dentro del mismo ChangeSet: para volver
a una revisión confirmada se abre un ChangeSet nuevo basado en ella. Los
payloads se limitan de tamaño y las operaciones masivas se representan por un
descriptor de selección reproducible y un resumen, no por un JSON sin límite.

## MULTI_ROUTE_ARCHITECTURE

`RouteWorkspaceState` se persiste por borrador y ruta con estos campos
independientes: `visible`, `active`, `editable`, `locked` y `dimmed`. Solo una
ruta puede ser `active`; puede haber muchas `visible`. La regla de autorización
es deliberadamente estricta:

```text
se permite editar = active AND editable AND NOT locked
visible no concede nunca permiso de edición
locked prevalece sobre cualquier otro estado
dimmed solo cambia representación, no datos ni permisos
```

La selección múltiple sirve para mostrar, encuadrar, comparar y validar varias
rutas. Una acción que muta datos exige una ruta activa y una confirmación que
identifica la entidad/ruta objetivo. Si la selección afecta a varias rutas, el
editor abre una operación por ruta o pide escoger; no replica cambios de forma
implícita. Las capas usan IDs internos y `feature-state`/fuentes GeoJSON
separadas por ruta para que ocultar o atenuar no fuerce recargar todo el mapa.

## MAP_EDITING_ARCHITECTURE

Se amplía el bridge QWebChannel a protocolo v2, manteniendo el v1 para la
navegación existente hasta que los tests de compatibilidad autoricen retirarlo.
La página MapLibre emite solamente gestos declarativos y acotados: selección,
inicio/fin de arrastre, inserción de vértice, solicitud de borrado y viewport.
Qt valida versión, tamaño, tipo de entidad, UUID, coordenadas WGS84 finitas y
estado de permisos; después llama a un caso de uso. Nunca llega SQL, HTML,
rutas locales ni una instrucción ejecutable desde JavaScript.

El flujo es: gesto -> propuesta visual temporal -> validación de aplicación ->
comando -> actualización de `draft_*` -> GeoJSON diferencial -> mapa. El mapa
no confirma una geometría por sí mismo. Mientras se arrastra se muestra una
previsualización; al soltar, la operación se confirma o se revierte con una
razón visible. `undo`/`redo` se ejecutan desde el controlador y refrescan solo
las entidades afectadas.

El editor soporta añadir/mover/borrar paradas, añadir/mover/borrar/reordenar
vértices, insertar en segmento y redibujar un segmento. Redibujar genera una
operación compuesta con el tramo previo y el nuevo; no sustituye silenciosamente
la geometría completa. La información de rutas no activas se entrega con un
presupuesto de puntos y simplificación por viewport existente; la ruta activa
recibe precisión completa dentro del límite de edición.

### ROAD / STREET ASSISTANCE

0.2.0 exige dibujo manual. Puede incluirse asistencia de snapping únicamente
si el basemap local expone geometría de calle consultable sin red y supera el
spike de precisión/rendimiento; será una sugerencia visible, aceptada por el
usuario y registrará el resultado como comando normal. La interfaz futura
`RoutingAdvisor` recibe segmento, perfil y límites, y devuelve alternativas o
«no disponible». No se implementan OSRM, Valhalla, backend, descargas ni
routing automático en 0.2.0.

## SCHEDULE_EDITING_ARCHITECTURE

La edición de `trips.txt`, `stop_times.txt`, `calendar.txt` y
`calendar_dates.txt` se presenta como una matriz de horarios y un editor de
servicios, no como CSV crudo. La matriz está vinculada a una ruta, patrón y
servicio, pagina viajes y conserva orden por `stop_sequence`. Las celdas
muestran el lexema GTFS, validan formato al confirmar y admiten 24:xx y 25:xx.

Añadir, quitar o reordenar una parada en un viaje abre el asistente de horarios
descrito arriba. «Ver interpolación» enseña valores y supuestos entre anclas
existentes; «Aplicar» crea `UPDATE_STOP_TIME` explícitos. Sin anclas válidas o
sin aceptación, los valores quedan vacíos/no resueltos y la validación lo
informa. No se deduce una frecuencia, viaje, calendario o shape desde una
geometría.

El editor de servicios permite modificar días, rango de fechas y excepciones
`calendar_dates`; detecta colisiones de `service_id`/fecha y viajes que usan el
servicio. Borrar un servicio exige reasignar los viajes o confirmar su borrado
como operación compuesta.

## OPERATOR_MODEL

Las agencias se modelan sobre `agency.txt`; la relación ruta-operador usa
`routes.agency_id`. `attributions.txt` se mantiene como una entidad GTFS
distinta: sus campos de colaborador, operador, autoridad y productor se editan
sin transformarlos en cuentas de usuario ni permisos de la aplicación. La UI
permite crear/editar agencias, asignar/desasignar rutas y gestionar
atribuciones. Antes de borrar una agencia, muestra rutas y atribuciones
referentes y requiere resolverlas. Todos los cambios se validan contra el
registro GTFS Schedule actual.

## VALIDATION_MODEL

Hay tres niveles, todos sobre el borrador efectivo:

| Nivel | Cuándo | Alcance |
| --- | --- | --- |
| Local | Al confirmar un campo o gesto. | Sintaxis, rangos, coordenadas, secuencias y referencias inmediatas. |
| Impactado | Tras aplicar un comando, con debounce/cancelación. | Entidades y reglas listadas en `impact`, como viaje, shape, ruta, servicio y dependencias. |
| Completo | Acción explícita, antes de confirmar y antes de exportar GTFS. | Registro de reglas completo, persistido como lote vinculado a revisión/ChangeSet. |

La validación impactada no sustituye a la completa. Los resultados se
identifican por revisión y ChangeSet para no mostrar incidencias obsoletas. El
editor indica errores, advertencias y cambios sin resolver sin impedir dibujar;
solo bloquea confirmación/exportación cuando el contrato del formato exige una
integridad que falta. El motor existente se amplía con contexto de revisión y
entidades afectadas, sin duplicar reglas en Qt o JavaScript.

## EXPORT_MODEL

Toda exportación 0.2.0 recibe una `ExportSelection` y una
`revision_id` explícita; por defecto apunta a la WorkingRevision, nunca al
original ni a un borrador no confirmado. La pantalla explica cuál se exporta.

| Salida | Contrato |
| --- | --- |
| Complete modified GTFS | ZIP GTFS completo de la WorkingRevision validada; conserva el original. |
| New GTFS version | Igual que el completo, con identificador de versión elegido por la persona usuaria y manifest lateral de revisión. |
| Selected routes GTFS / Mini-GTFS | Calcula cierre de dependencias: rutas -> agencias, viajes, servicios/calendarios, stop_times, paradas, shapes, frecuencias, atribuciones y archivos opcionales que las referencian. Muestra lo incluido/excluido antes de publicar. |
| JSON / CSV / GeoJSON | Reutiliza contratos actuales, documentando revisión y filtro; no se ofrece reimportarlos como GTFS completo. |
| KML / KMZ | Intercambio geoespacial, no un sustituto de GTFS Schedule. |

Las salidas usan el escritor atómico y manifest de hashes actuales. Mini-GTFS
mantiene su reimportación interna y validación previa. Un borrador puede
previsualizarse, pero no se etiqueta ni se exporta como versión GTFS hasta
confirmarse.

## KML_KMZ_CONTRACT

La exportación produce KML estándar con `Placemark`, `Point`, `LineString`,
`Style` y `ExtendedData`. Ofrece los perfiles `STANDARD_KML`, `GOOGLE_EARTH` y
`GOOGLE_MY_MAPS`; el perfil solo adapta compatibilidad de estilos/metadata, no
inventa entidades GTFS. Cuando sea seguro, `ExtendedData` porta
`route_id`, `route_short_name`, `route_long_name`, `agency_id`, `shape_id`,
`stop_id` y `stop_sequence`, además de una versión de metadata de GTFS
Explorer. KMZ contiene el KML principal y recursos estrictamente locales que
el perfil admita.

La importación clasifica el archivo antes de crear datos:

1. `GTFS_EXPLORER_KML`: metadata íntegra y versión compatible; puede hacer
   round-trip de las entidades geográficas representadas, pero exige comprobar
   que la revisión de destino es compatible.
2. `MODIFIED_KML`: metadata parcial o modificada; abre asistente de mapeo con
   candidatos y confirmación por entidad.
3. `UNKNOWN_KML`: `LineString` propone una ruta/shape y `Point` una parada;
   abre un asistente geoespacial y nunca proclama haber importado un GTFS
   completo.

Para KML modificado o desconocido, agency, route, services, trips y horarios
que falten se solicitan explícitamente o quedan sin resolver. No se exportan
ni confirman hasta cumplir las reglas aplicables.

## KML_KMZ_SECURITY_MODEL

KML/KMZ reutiliza el confinamiento de ZIP de importación y añade un parser XML
seguro. Por defecto rechaza `DOCTYPE`, `ENTITY`, `SYSTEM`, `PUBLIC`, XInclude,
enlaces de red, rutas absolutas/normalizadas fuera de raíz y miembros no
regulares. No descarga iconos, `NetworkLink`, overlays ni recursos externos.
La descripción HTML se guarda como texto y se escapa/sanitiza al mostrarla;
nunca se inyecta en WebEngine.

El adaptador impone límites configurables y cubiertos por pruebas: miembros,
tamaño comprimido y descomprimido acumulado, ratio de expansión, tamaño XML,
profundidad, atributos, texto por nodo, puntos por geometría y número de
features. Procesa streaming donde sea posible, cancela cooperativamente y
limpia temporales en error. Los valores iniciales se fijarán junto al spike de
CTM/KML y no se relajarán sin benchmark y test de abuso. Los errores se
presentan como fichero no seguro/no compatible, sin exponer rutas internas.

## PERFORMANCE_MODEL

DuckDB conserva escritor único y consultas paginadas. Crear/confirmar un
borrador debe ejecutar por lotes y con progreso/cancelación; el mapa actualiza
solo fuentes/capas afectadas, mantiene el cache por viewport y evita recargar
el WebEngine. La vista de horarios pagina por patrón/viajes; nunca carga todos
los `stop_times` en un widget. `ValidationImpact` limita recomputación, y el
usuario puede solicitar validación completa.

Los presupuestos y perfiles se definen antes del primer slice funcional:
apertura de proyecto 0.1.0, creación de borrador CTM, arrastre continuo,
confirmación, undo/redo, matriz de horarios, validación impactada y exportación
parcial. Se reportan por separado tiempo, memoria, disco temporal y tamaño de
historial. No se promete edición fluida de un feed grande hasta medirlo.

## TEST_MODEL

Las pruebas siguen la separación Product / Engineering / Artifacts y añaden:

- unitarias de serialización, precondiciones, aplicación/inversión de comandos,
  undo/redo, ramas y estado dirty;
- integración DuckDB de snapshots, atomicidad, inmutabilidad del original,
  recuperación de borrador y migraciones 0.1.0 -> 0.2.0;
- casos GTFS de paradas, shapes, stop_times, servicios, agencias y
  atribuciones, incluidos horarios 24:xx/25:xx y dependencias no resueltas;
- UI Qt/MapLibre para permisos multirruta, gestos, overlay diferencial y
  bridge v2 inválido/ordenado/acotado;
- exportaciones completas/parciales, cierre de dependencias, Mini-GTFS,
  perfiles KML/KMZ y round-trip clasificado;
- seguridad KML/KMZ: ZIP Slip, zip bomb, XML con entidades/DOCTYPE, XML
  excesivo, paths peligrosos, NetworkLink y HTML hostil;
- E2E de proyecto nuevo, apertura/migración 0.1.0, guardar/descartar/confirmar,
  paquete Portable/Setup y aceptación visual Windows separada del smoke.

Los fixtures siguen siendo ficticios o autorizados. Los gates registran
`PASS`, `FAIL`, `HANG`, `OBSERVATION`, `BLOCKER` o `NOT VERIFIED`; un smoke
técnico no sustituye la aceptación visual nativa.

## MIGRATION_MODEL

Los proyectos 0.1.0 deben abrirse en 0.2.0. La primera apertura aplica una
migración DuckDB transaccional y con backup que:

1. registra la versión de esquema editorial y usa `original` como revisión 0 implícita;
2. preserva staging y tablas normalizadas sin modificar sus valores;
3. genera `EntityKey` estables para entidades existentes;
4. crea `editor_state`, `editor_history`, `editor_deltas` y
   `editor_revision_deltas` sin materializar un snapshot inicial;
5. crea un borrador limpio y actualiza `project.json` de forma compatible.

Si no puede terminar, se restaura el backup y el proyecto permanece abrible
por 0.1.0. La migración es idempotente, muestra progreso y no elimina un
proyecto 0.1.0. 0.1.0 no necesita entender un proyecto ya modificado por 0.2.0;
la UI debe advertirlo antes de la primera confirmación de edición. Se probarán
proyectos sin feed, con recovery, con validaciones históricas y con archivos
opcionales.

## IMPLEMENTATION_ORDER_FOR_LUNA

Una secuencia continua, con checkpoints internos y sin macrofases externas:

1. Fijar contratos de dominio, límites y ADRs 0.2.0; inventariar tablas y
   relaciones GTFS existentes. **Checkpoint A:** contrato revisado, sin código
   funcional.
2. Crear migraciones y repositorios de Original/Working/Draft/Revision,
   EntityKey y ChangeSet; cubrir backup, rollback e inmutabilidad. **Checkpoint
   B:** abrir un proyecto 0.1.0 crea un borrador limpio reversible.
3. Implementar Command/ChangeSet, historial, dirty/save/discard/commit y
   undo/redo exclusivamente para `UPDATE_STOP` y `MOVE_STOP`. **Checkpoint C:**
   persistencia y recuperación superan tests de atomicidad.
4. Añadir validación local/impactada vinculada a comando y el panel de cambios;
   conservar validación completa existente. **Checkpoint D:** incidencias no
   obsoletas y confirmación protegida.
5. Extender el bridge v2 y MapLibre para selección y arrastre seguro; conectar
   el único `MapWidget` al caso de uso de paradas. **Checkpoint E:** gesto,
   undo/redo y permisos no generan SQL ni mutan el mapa sin comando.
6. Incorporar estados multirruta, selección/visibilidad/capas diferenciales y
   bloqueo de edición; después shapes y vértices. **Checkpoint F:** cuatro
   rutas simultáneas y protección contra edición accidental.
7. Implementar matriz de horarios, operaciones explícitas de stop_times,
   trips y servicios, incluido asistente de interpolación solo bajo aceptación.
   **Checkpoint G:** casos 24:xx/25:xx y datos no resueltos cubiertos.
8. Implementar agencias, asignación de rutas y attributions con sus
   dependencias. **Checkpoint H:** reglas de borrado/reasignación verificadas.
9. Generalizar exportación por revisión y selección, incluyendo cierre de
   dependencias, GTFS completo y Mini-GTFS. **Checkpoint I:** exportación no
   toca original y reimporta cuando el contrato lo exige.
10. Implementar KML/KMZ seguro, perfiles y asistente de clasificación, sin
    routing automático. **Checkpoint J:** corpus malicioso y round-trips
    clasificados pasan.
11. Ejecutar benchmarks CTM, optimizaciones justificadas, E2E, build,
    Portable/Setup y aceptación visual Windows. **Checkpoint K:** evidencia
    de release 0.2.0 clasificada, sin alterar 0.1.0.

## RISKS

| Riesgo | Control |
| --- | --- |
| Materializar el feed completo en memoria puede ser costoso en CTM. | Mantener el riesgo explícito; persistir solo deltas y aplazar lazy loading/compactación hasta una regresión real. |
| Gestos de mapa y relaciones GTFS pueden crear incoherencias. | Comandos transaccionales, precondiciones, validación impactada y confirmación explícita. |
| KML es ambiguo y hostil. | Clasificación conservadora, asistente, parser sin red/entidades y corpus de seguridad. |
| Bridge WebEngine amplía superficie. | Protocolo versionado, allowlist de mensajes, límites, IDs internos y tests de mensajes malformados. |
| Multirruta induce edición equivocada. | Ruta activa única, lock prioritario, confirmación de destino y señalización visual. |
| Migración daña proyectos existentes. | Backup transaccional, idempotencia, rollback y apertura de fixtures 0.1.0 reales autorizados. |
| Routing automático amplía coste/infraestructura. | Fuera de 0.2.0; solo interfaz y asistencia local viable. |

## STOP_CONDITIONS

Se detiene el avance y se solicita decisión si ocurre cualquiera de estas
condiciones:

- no es posible preservar/abrir un proyecto 0.1.0 tras una migración reversible;
- la reconstrucción `ORIGINAL_GTFS + cadena de deltas` no puede abrir un feed
  real dentro del límite de memoria y requiere una decisión de arquitectura;
- una operación no puede expresar `before`, `after`, impacto e inversa segura;
- la seguridad KML/KMZ exige red, un parser no controlable o relajar límites
  sin evidencia;
- MapLibre/bridge no puede distinguir un gesto de una mutación autorizada;
- el routing requiere OSRM, Valhalla, backend, datos o costes nuevos;
- la validación completa o exportación producen un GTFS que no supera sus
  contratos de reimportación/seguridad;
- un gate de paquete/Windows queda sin evidencia terminal o la aceptación
  visual nativa revela una regresión.
